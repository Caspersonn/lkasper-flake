# Design

## Context

- kaito (x86_64, i3-1315U, 15 GB RAM, single NVMe with ~176 GB free) is a self-contained host in `modules/hosts/kaito/configuration.nix`; it already imports `docker` (oci-containers backend `docker`), `networking-nebula` (network `mesh`, kaito = `10.123.0.1`), `tailscale` and `secrets`.
- The NixOS firewall is global today; only `adguardhome.nix` scopes ports to an interface (`enp86s0`). Nebula's own firewall allows all inbound traffic.
- Existing container modules (`aiostreams.nix`, `twenty.nix`) publish ports through Docker. Docker-published ports are DNAT'ed in the `nat`/`FORWARD` chains and bypass the NixOS `INPUT` rules, so they cannot be limited per interface with `networking.firewall.interfaces`.
- HolyArrs has no published binaries and refuses to run as root outside a container; it ships as a `FROM scratch` image with a built-in healthcheck. Decypharr ships as the `cy01/blackhole` image with FUSE and rclone inside. Jackett is packaged in nixpkgs with a NixOS module. Neither HolyArrs nor Decypharr is in nixpkgs.
- HolyArrs only follows symlinks when `HOLYARRS_FOLLOW_LINKS=1` is set; it then places imported links in the library as links. Symlinks only resolve if every service sees the mount at the same absolute path.
- The four acquisition modules already exist. Historical build and VM results in `implementation-notes.md` verify that baseline, not declarative first-run provisioning or a complete playback stack.
- The confirmed workflow is discovery outside the owned music library, a HolyArrs acquisition request, a wait, and automatic playback. Music and movie/TV applications must be separate.

## Goals / Non-Goals

**Goals:**
- One shared `/data` tree with identical paths on the host and in every container, readable by the selected playback services.
- Private-only management interfaces enforced by the NixOS firewall, not by convention.
- No-clickops provisioning from repository-managed settings and protected runtime secrets, including on a fresh installation.
- Home Manager manages supported user application configuration and dotfiles; NixOS manages server services and their configuration.
- Preserve existing services and library data until the replacement passes end-to-end acceptance.
- Everything removable by dropping the imports from kaito.

**Non-Goals:**
- Removing existing libraries or services before replacement acceptance.
- Requiring YouTube or paid streaming as a substitute for music acquisition.
- Local torrent clients (including Transmission), a torrent VPN, Usenet, Prowlarr, FlareSolverr.
- Reusable multi-host defaults; the modules are written for kaito's layout and are x86_64-tested only (both images also publish arm64, but server-casper is not a target).

## Decisions

### NixOS services and Home Manager dotfiles
Keep shared daemons, containers, mounts, firewall rules and service-owned `/var/lib` state in NixOS modules. Add supported client packages and non-secret dotfiles through `flake.modules.homeManager` under `modules/users/shared/`, composed into explicitly selected user profiles. `modules/users/shared/meridian.nix` demonstrates `xdg.configFile` management, and `modules/users/casper/home-manager.nix` composes shared modules.
Web applications may have no local dotfiles; their settings still belong in repository-managed server provisioning. Selected client profiles are `casper@technative-casper`, `casper@gaming-casper` and `casper@personal-casper`. Wire client imports only into those profiles, including their NixOS-integrated Home Manager equivalents; do not add unconditional client imports to the shared Casper module used by other hosts.
*Alternative:* move the entire stack into Home Manager. Not selected because shared mounts, system accounts, containers and firewall belong to the host lifecycle rather than a login profile.

### Declarative provisioning replaces first-run setup
Manage non-secret intent in Nix and keep secret inputs encrypted with agenix. Prefer supported configuration files and secret-file inputs. For API-only settings, use systemd-managed idempotent reconciliation with runtime credentials, readiness checks, bounded retries and explicit failures. Reconcile only owned settings; preserve library records, listening history and user activity.
Bootstrap must cover owner accounts and API credentials: a script requiring a key first created in a web UI does not meet the requirement. Verify every bootstrap mechanism against its pinned version. Render secret-bearing configuration outside the Nix store with restricted permissions, never into derivation arguments or logs. Rebuilds must converge managed settings without duplicating integrations.
*Alternatives:* manual wizards, manual API commands or SQLite edits. Not selected because they do not provide the required reproducible lifecycle.

### Implementation gates for the expanded scope
The requirements are confirmed, but the expanded stack is not ready for activation. Resolve each component's acquisition and bootstrap design before implementing that component, recording concrete tasks and tests first. Independently testable provisioning components may be implemented while other components remain under investigation. This staged approach allows testing the verified configuration-file contracts without claiming that the full-stack bootstrap or playback gates have passed:

- Soundspan is selected by the user as the music application, conditional on verifying the required HolyArrs workflow. Jellyfin is selected for movie/TV playback. Client profiles are `casper@technative-casper`, `casper@gaming-casper` and `casper@personal-casper`.
- Verify discovery, request submission to HolyArrs, availability refresh and automatic first playback. Soundspan documents Lidarr integration; HolyArrs documents Sonarr/Radarr compatibility, not Lidarr compatibility. A native HolyArrs adapter may be needed; neither an adapter nor a turnkey integration has been verified.
- The user selected the existing paid Real-Debrid service for music via HolyArrs and Decypharr, superseding the subscription-free acquisition and Transmission/VPN proposals. Use the existing mount and symlink storage policy; verify music category routing, import and playback at the pinned versions. Select and verify concrete Jackett music sources without requiring another subscription.
- Verify unattended bootstrap, settings reconciliation and credential/key recovery for every selected service at its pinned version. Current HolyArrs documentation describes newer releases than the implemented `1.0.19`; documentation alone does not prove version support.

Unresolved acquisition and bootstrap choices block their dependent components and full-stack activation, not independent contract tests. Discovery and a revised concrete design must precede each component's implementation; full workflow verification is an acceptance gate after implementation. Comments in code are not needed.

### Soundspan integration investigation

Soundspan's music discovery search uses Last.fm artist and track searches; podcast search uses iTunes independently. The backend receives `LASTFM_API_KEY` from the existing agenix `music-lastfm` environment file when that secret is declared. This reuses the existing free metadata credential without adding an acquisition subscription. Configurations without agenix or the declared secret omit this environment file. Comments in code are not needed.
Inspected Soundspan source revision `207d412ab380de7e4e0af11daecd6a2f82f86857`; this identifies the research snapshot, not a selected deployment version.

- [Soundspan integrations](https://soundspan.io/docs/integrations) documents Lidarr acquisition and import webhooks, not a HolyArrs connection. Its separate Soulseek path does not demonstrate acquisition through HolyArrs.
- At the inspected revision, `backend/src/services/lidarr/lidarrArtistCatalog.ts` calls `/api/v1/album?artistId=...` and posts `RefreshArtist` to `/api/v1/command`. `backend/src/services/lidarr/lidarrQueue.ts` relies on Lidarr queue/history schemas and the `AlbumSearch` command. These are protocol and data-model dependencies, not just a configurable server URL.
- [HolyArrs old-app API](https://docs.holyarrs.com/reference/old-app-api/) documents only Sonarr/Radarr compatibility. Pointing Soundspan's Lidarr setting at HolyArrs is not a verified solution.

The user approved building a custom Soundspan-to-HolyArrs integration. The required workflow has not passed an end-to-end test. Do not substitute Soundspan's direct downloader and silently bypass HolyArrs. Task 0.2 stays open, including availability refresh and automatic playback verification.

### Custom integration direction
Use a native HolyArrs acquisition provider in a repository-managed patch to pinned Soundspan source, rather than implementing a general Lidarr compatibility server. This avoids emulating Lidarr artist/catalogue/queue/history semantics and exposing its library-cleanup operations. This is the implementation direction, not an implemented or verified integration.

Inspected HolyArrs tag `1.0.19`, source revision `3a710bab9e157dc68385da4f3f7e96b957f6617e`, matching the existing container tag. Source inspection establishes these contracts; runtime and image/source correspondence still need testing:

- `app/backend/internal/requests/routes_asks.go` accepts `POST /api/v1/asks` with `{"kind":"artist","id":"mbid:<artist MBID>","albums":["<release-group MBID>"]}`. Always send a nonempty explicit album list: an empty list requests the whole artist. The response wraps the request in `ask`; duplicate requests can return HTTP 200 instead of 201.
- `GET /api/v1/asks/{id}` returns the request view directly. Request states include `asked`, `approved`, `turned_down` and `available`. HTTP 409 can include `title_id` and `ready` for an item already in the library; other conflicts must remain failures rather than being treated as success.
- `app/backend/internal/accounts/setup_owner.go` implements owner creation at `POST /api/v1/auth/setup`, establishes a setup session and rejects creation if an owner already exists. `routes.go` registers login, setup completion and API-key routes. This supports further unattended-bootstrap investigation but does not yet verify credentials, CSRF/session handling or key recovery. Keep a fresh service inaccessible to other clients until owner bootstrap succeeds, because the first caller can claim ownership.
- `app/backend/internal/downloads/routes_downloaders.go` lists Transmission among supported downloader kinds and supports music-specific categories. Its request handling does not establish a Soulseek integration.

At the inspected Soundspan revision, `downloadSourcePolicy.ts` restricts providers to `tidal`, `lidarr`, `soulseek` and `youtube`; `downloadDispatcher.ts` dispatches Lidarr through `simpleDownloadManager`. Add HolyArrs explicitly to provider selection, dispatch, persistent job reconciliation and the corresponding settings/UI types. Do not disguise it as Lidarr or inherit the legacy automatic fallback order. HolyArrs-only mode must fail visibly when unavailable rather than dispatch to another source.

Persist the HolyArrs request identifier with the Soundspan job and reconcile pending requests after restart. An `available` request is a trigger to refresh Soundspan's library, not proof that Soundspan can play it. Resolve imported albums by MusicBrainz identity, verify playable tracks, then notify the requesting client to start its explicitly requested playback. Background completion must not unexpectedly start unrelated sessions. Preserve a visible pending state while metadata, acquisition or import is incomplete; surface rejection and errors with retry. Verify bounded retry, duplicate submission, already-owned media, refresh failure and restart recovery in contract tests and a disposable-VM end-to-end test before enabling the provider on kaito.

### Music acquisition through the existing Real-Debrid service
The user approved reusing the existing paid Real-Debrid subscription for music and dropping Transmission/VPN. This supersedes the earlier subscription-free acquisition requirement and local-file downloader proposal. Soundspan, HolyArrs, Decypharr and Jackett must not require an additional app, music-streaming or VPN subscription; YouTube is not a fallback.

Route music requests through HolyArrs → Decypharr → Real-Debrid and import symlinks from `/data/symlinks` into `/data/media/music`, resolving under `/data/debrid` everywhere. Retain service state, artwork and bounded operational caches locally, not a complete retained music copy. Verify that Soundspan scans and plays these links and does not require copying the library into its own container. Mount loss must yield visible unavailability, not writes of complete media files into the empty mount point.

Torrent acquisition happens on Real-Debrid's infrastructure; kaito must not join peer swarms or fall back to local torrenting. Peers do not receive the home's public IP through this acquisition path, but Real-Debrid and directly contacted metadata/indexer services can see it. This is not a promise of anonymity from providers. No VPN, local torrent listener, seeding settings or tunnel credentials are needed for this design.

Music availability remains dependent on indexed releases and Real-Debrid's ability to fetch them. Existing movie VM tests do not establish album availability, music category routing or playable imports. Verify a real album and report an unavailable release honestly rather than bypassing HolyArrs. The user selected Knaben and The Pirate Bay; live source availability remains unverified.

### Independent modules under `modules/services/tools/`
`media-storage.nix`, `holyarrs.nix`, `decypharr.nix`, `jackett.nix`, `media-connections.nix` and `media-backup.nix`, each `{ inputs, ... }: { flake.modules.nixos.<name> = ...; }`, imported explicitly by kaito. Keep acquisition services, connection reconciliation and backup handling independently composed; adding the music workflow does not introduce a second downloader.
*Alternative:* one `holyarrs.nix` holding the whole stack. Rejected: harder to swap parts, and no existing module in `modules/services` imports another one, so cross-module imports would be a new pattern.

### Containers use host networking
Both containers run with `--network=host` and no `ports`. The NixOS firewall governs the HolyArrs access socket on 6262 and Decypharr on 8282 like host services, and HolyArrs reaches Jackett (`127.0.0.1:9117`) and Decypharr (`127.0.0.1:8282`) over loopback. HolyArrs itself binds only `127.0.0.1:6263`; a systemd socket proxy exposes 6262 only after its owner/API bootstrap succeeds. Stopping or failing the container stops its access socket and proxy.
Ports are opened only via `networking.firewall.interfaces."nebula.mesh"` and `networking.firewall.interfaces.${config.services.tailscale.interfaceName}`; `nebula.mesh` is the default tun name for network `mesh` and is checked on kaito before deploying.
*Alternatives:* publish on `127.0.0.1` and add an nginx listener on the mesh address (extra moving part, nginx needs the Nebula IP up before it starts); publish on `10.123.0.1:6262` (Docker fails to start the container if Nebula is not up yet, and does nothing for Tailscale); bridge network with `host.docker.internal` (Jackett would have to listen on the Docker bridge).

### Decypharr mounts Real-Debrid itself and propagates it to the host
Decypharr uses its built-in `dfs` FUSE mount at `/data/debrid`, with `/dev/fuse`, `SYS_ADMIN` and the host's `/data` bound as `/data:/data:rshared`, so the mount appears on the host. HolyArrs binds `/data:/data:rslave` so it sees the mount even if it started first. `allow_other` is switched on in Decypharr so other uids (later Jellyfin) can read it.
The Docker unit gets a lazy unmount of `/data/debrid` before start and after stop, so a crashed container (or kaito losing power) does not leave a dead "Transport endpoint is not connected" mount behind. After confirming the underlying directory is not mounted or a symlink, pre-start assigns it to media at 2770; mounted ownership is never changed. Actual-container VM testing found that the root-owned 0755 underlay prevented the non-root FUSE process from mounting even though its API started. A bounded post-start mount check now refuses API-only startup without a host-visible FUSE mount.

The gated HolyArrs socket disables default socket ordering and explicitly retains shutdown conflicts. Actual full-boot VM testing exposed a cycle through `sockets.target` and `basic.target` when the socket waited for container provisioning. It remains ordered after successful container startup, rather than opening early to avoid that cycle.
*Alternatives:* a host-side rclone mount of Decypharr's WebDAV (`external_rclone`) — removes FUSE from the container but adds an rclone unit, RC credentials and an unverified path contract; Decypharr's NFS server — another daemon and mount unit for no gain in a test setup.

### One `media` identity owns `/data`
`media-storage.nix` creates a `media` system user and group with a fixed uid/gid (2000), passed to both containers as `PUID`/`PGID` with `UMASK=002`, and adds `casper` to the group. `/data` itself is `root:root 0755` (tmpfiles refuses service-owned children under a non-root parent, as in `slskd.nix`); `/data/{symlinks,media,media/movies,media/tv,media/music}` are `media:media 2770` and `/data/debrid` is an empty mount point.
*Alternative:* separate users per container in a shared group. Rejected for now: both write the same tree and HolyArrs never needs to be isolated from Decypharr's files; Jellyfin will join the group later.

### HolyArrs settings that matter
Pinned `holyarrs/holyarrs:1.0.19`, registry digest `sha256:0d82787b6bd274bd19b31adee9689f90e55d4c46a8194594deecfe02882d963d`, fetched as a fixed-output image for linux/amd64; `/var/lib/holyarrs:/config`; environment `PUID`, `PGID`, `UMASK`, `TZ` (from `config.time.timeZone`), `HOLYARRS_FOLLOW_LINKS=1`, `HOLYARRS_SAVE_PATH=/data/symlinks`, `HOLYARRS_HEALTH_URL=http://127.0.0.1:6263`, and `HOLYARRS_ALLOWED_HOSTS` with `kaito.mesh` so the mesh hostname is accepted (IPs are allowed by default). The systemd unit is ordered after Decypharr's but does not require it, so a Decypharr restart does not take HolyArrs down. Startup runs the owner/API provisioner before becoming active, with a 120-second timeout and three automatic attempts per five minutes.

### Decypharr settings that matter
Pinned `cy01/blackhole:v2.7.2`; `/var/lib/decypharr:/app` (it runs `chown -R` on `/app` at start, so it must not share that directory with anything). The baseline leaves the Real-Debrid key, login, mount type, `download_folder=/data/symlinks` and category to a first-run wizard. Replace that setup with verified unattended provisioning. First-start handling of environment overrides must be tested; do not assume environment variables alone bypass the wizard.

### Jackett via the NixOS module
`services.jackett.enable = true` with `openFirewall = false`; 9117 is opened on the mesh interfaces like the others. Declare the HolyArrs link to `http://127.0.0.1:9117` and local-network access in provisioning. Indexer definitions and categories must be reproducible without UI configuration; credentials are protected runtime inputs or generated persistent state.

Inspected the repository's nixpkgs Jackett version `0.24.2586` and matching upstream tag `v0.24.2586`. `ConfigurationService` reads `ServerConfig.json`; `IndexerConfigurationService` reads `Indexers/<id>.json` as configuration-item arrays. `BaseIndexer.LoadFromSavedConfiguration` loads these without making an external search. Configure `knaben` and `thepiratebay` before starting Jackett, using their packaged category mappings. Both advertise generic-query music search. Set TPB's `Top100` to `100` (Audio) so keyword-less music tests do not depend on its movie-heavy recent list; keyworded movie/TV searches remain supported. The dynamic setting IDs come from display labels (`apiurl`, `top100`), not arbitrary Torznab categories.

Use a pre-start renderer running as the Jackett service user while the main process is stopped. Generate API key, instance identity and an administration password once in protected `provision-auth.json`, then atomically render `ServerConfig.json` and reconcile only owned source items. Jackett hashes the administration password using SHA-512 over UTF-16LE password plus API key. Preserve unknown settings and other indexer files; refuse malformed state, mismatched credentials or pre-existing unmanaged server state rather than resetting credentials. Persist the credential seed before dependent files so interrupted first installation can resume. Keep all generated files at 0600 under the existing 0700 data directory. The existing encrypted Jackett-state backup covers them. No account enrollment or new plaintext repository secret is required.

Add unit tests for repeat provisioning, state preservation, refusal and interruption recovery, and a separate NixOS check using the real packaged Jackett process. Verify authenticated local Torznab capabilities and source configuration after two activations without external tracker traffic. This does not establish that live album searches or HolyArrs integration work; task 8.2 remains open until those checks pass. Comments in code are not needed.

Jackett's Torznab error responses use HTTP 200 with an XML `error` element, including code `100` for an invalid API key. Check that payload rather than interpreting HTTP success as authenticated access; this source contract was also observed in the actual-service VM test.

### Credentials and recovery
Replace the original UI-only credential decision with agenix-backed runtime provisioning or protected automatic generation. Preserve service-generated keys and databases together and restore them through an automated recovery procedure. HolyArrs' actual key path is `/var/lib/holyarrs/holyarrs.key`; its own backup excludes that key, so application backups alone are insufficient. Supported bootstrap and recovery mechanisms remain gated on version-specific investigation.
*Alternative:* manual entry and copying keys into a password manager. Not selected because clean-machine setup and recovery would still depend on clickops.

### User-selected local backup storage
The user approved encrypted bootstrap state under `secrets/` and backups on the server for now. Keep mutable service databases in their normal `/var/lib` directories, not in Git or the Nix store. Store the restic repository at `/var/backups/media/restic`, root-only, and enroll its randomly generated password as `secrets/media-backup-password.age` for the owner and kaito. No remote storage or additional subscription is introduced. These same-server backups protect retained snapshots, not against losing the server's disk.

Implement the independently testable acquisition-state component as `media-backup.nix`, imported only by kaito. Back up `/var/lib/decypharr`, `/var/lib/holyarrs` and `/var/lib/jackett`, including Decypharr auth/signing state and the actual `holyarrs.key`, while excluding Decypharr's bounded streaming cache. Stop the acquisition state writers for a consistent snapshot, record which services were active in a root-only runtime journal, and restart only those services in reverse order on success or failure. Use a shared lock and systemd cleanup to recover from interrupted backup commands. Check repository access before stopping services. Create snapshots with a pending tag and promote only a successful completed snapshot to the restore/retention tag; failed or partial snapshots must not be selected for restore or trigger pruning. Schedule daily backups with seven daily and four weekly snapshots. Do not activate a new system generation or manually start writers during a snapshot.

Restore first into a fresh root-only staging directory under `/var/lib/media-restore`, verifying the selected snapshot and refusing an existing nonempty target. This independently verifies encrypted state recovery without overwriting live application state. Automated clean-machine installation from staging, symlink-tree recovery and application-specific validation remain explicit follow-up tasks, not established by a staging restore. Extend consistency handling and backup coverage for Soundspan/PostgreSQL and Jellyfin after their bootstrap/storage contracts are resolved; never assume copying a running PostgreSQL directory is consistent. Comments in code are not needed.

### Pinned bootstrap source investigation
Inspected HolyArrs `1.0.19` source revision `3a710bab9e157dc68385da4f3f7e96b957f6617e` and Decypharr `v2.7.2` revision `d6f8df094dfe58eff16932f64c5e13bc24ae1d3a`. These are source contracts, not a successful fresh-instance or recovery test:

Use a private cookie jar and `X-CSRF-Token` on authenticated mutations. `core/webserver/caller.go` accepts session or API-key authentication for `RequireStrong`; do not rely on the local-network bypass. `accounts/keys.go` creates keys through `POST /api/v1/auth/keys` with a label and scopes and returns the plaintext key only once. Persist the returned key atomically with restricted access; listing keys cannot recover a lost value. `accounts/assurance.go` rotates the session and CSRF value on reauthentication and implements owner-only `POST /api/v1/auth/setup/done` to finish the wizard. Verify the whole sequence, safe retry/reconciliation and scoped permissions at runtime before enabling it. Do not repeatedly create keys on activation or reset an existing owner.
- Decypharr `internal/config/config.go` reads `config.json` and separate `auth.json`, applies defaults, then environment overrides. Setup completion is configuration validation, not an independent wizard-completion flag. Use runtime-rendered configuration rather than browser wizard actions. Select token-only authentication: `pkg/server/qbit/context.go` accepts the API token as the qBittorrent login password, independently of the username. Generate and persist the token once; HolyArrs will read it at runtime. Runtime compatibility with HolyArrs remains an acceptance test, not a source-inspection result.
- Decypharr defaults categories to `sonarr` and `radarr`. Declare music routing explicitly and verify `allowed_file_types`, music file-size filtering and DFS mount settings instead of assuming the movie defaults cover albums. Render credentials outside the store before starting the service, preserve generated signing secrets, and test repeated activation rather than replacing persisted state blindly.

Soundspan revision `207d412ab380de7e4e0af11daecd6a2f82f86857`, `backend/src/routes/onboarding.ts`, exposes `GET /api/onboarding/status` with `hasAccount` and `needsOnboarding`. `POST /api/onboarding/register` accepts username/password only when no user exists and returns an admin user plus JWT. Authenticated `POST /api/onboarding/complete` records completion. Keep first-run registration inaccessible to other clients; this route checks user count before account creation, not inside a serialized transaction. Existing accounts require normal login and identity/role verification, not another registration. The existing Lidarr onboarding endpoint cannot configure HolyArrs; the approved provider patch must add supported settings/API access. These source contracts do not establish complete settings reconciliation or recovery.

Soundspan settings/login/recovery and Jellyfin bootstrap/recovery contracts still need version-specific investigation. Jackett's file-based provisioning design is recorded above; complete application recovery remains unverified. Task 0.4 remains open; no-clickops acceptance is not established by these source reads.

### HolyArrs owner and native API bootstrap
Implement an independently testable Python API provisioner against `1.0.19`, using a loopback-only HTTP endpoint with proxy environment variables and redirects disabled. Keep cookies and CSRF tokens in memory. Readiness polling retries only the initial read with a fixed deadline; do not blindly retry mutations. Generate the `media-admin` owner password once in a protected `provision/owner.json` below the existing HolyArrs state directory before submitting setup. Existing owners without that seed require explicit migration; never reset them or generate replacement credentials. Login must confirm the expected owner identity and role.

Manage one native API key labelled `nixos-media-provision`, persisted atomically as `provision/api-key.json`. Before creating it, write a protected creation-intent journal. If creation was interrupted before its one-time response was saved, use the authenticated owner session to revoke only matching managed-label orphan keys and retry creation. A missing key without that pending journal requires restore rather than rotation; an existing key must authenticate and match its recorded identifier, label and scopes. Clear the journal before signalling completion. Finish the owner setup through the supported API, verify `setup_open` is false, and log out the temporary session. No database editing or manual key retrieval is used. Both seed and API state are included in the existing encrypted HolyArrs-directory backup. Comments in code are not needed.

Before host wiring, verify contracts with a local fake server and the actual pinned container on a disposable, loopback-published test port with fresh fixture state. These tests do not configure libraries, downloaders or sources, and do not complete 8.3 or 0.4. Production wiring must prevent mesh clients claiming the first owner: run the application on a loopback-only backend and expose its existing private management port through a systemd-gated socket proxy only after bootstrap succeeds. Verify restart and failure ordering in a NixOS VM before changing production exposure; do not rely on a transient firewall rule that a firewall reload could remove.

The actual `1.0.19` container can reuse a deleted API-key row identifier. Orphan recovery must verify that the previous key value is rejected and the new value authenticates; a different numeric identifier is not a valid recovery assertion.

Reconcile only `skip_login_local_network=false` through `GET/PUT /api/v1/auth/settings`, authenticated with the managed native key, and verify it before exposing access. A TCP socket proxy presents a loopback peer to the application, so local-network login bypass must remain disabled. Other sign-in settings are preserved. Run the provisioner as the existing media identity with a 0700 state directory and 0600 files, consistent with the container's configuration ownership. Set `HOLYARRS_HEALTH_URL` to the loopback backend; the image's built-in health command otherwise probes its default port. The production backend uses 6263, while the private management socket retains 6262. Fetch the verified image digest through a fixed-output Nix image derivation so the VM and production configuration test the same image content.

### Decypharr runtime renderer
Implement the renderer under `modules/services/tools/media-provision/` before wiring it into the active host. Its input is a protected runtime JSON credential file containing `real_debrid_api_key`; do not invent a placeholder credential or fetch it during Nix evaluation. Read existing configuration and auth state, preserve signing secrets, API tokens and unmanaged settings, and reconcile only the declared acquisition settings. Reject malformed existing state rather than recreating accounts or losing keys. Write only changed files using restricted temporary files, atomic replacement and fsync; never print credential values.

Declare the shared symlink drop folder, the `holyarrs-movies`, `holyarrs-tv` and `holyarrs-music` categories, Real-Debrid as the only acquisition provider, and `default_download_action=symlink`. Allow video and audio extensions explicitly, with no minimum size filter that would exclude short tracks. Use DFS at `/data/debrid` with a 500 MB disk cache and 256 MB streaming-buffer budget; the pinned Linux DFS backend already sets `AllowOther=true`, so there is no invented `allow_other` JSON option. Disable unused WebDAV, NFS and SMB endpoints. Preserve existing torrent/job state outside these configuration files.

Actual image testing revealed that Decypharr also enables Hearsay peer discovery and publishing by default. Explicitly set `hearsay.disabled=true`, `participate=false` and `publish=false`, as supported by pinned `internal/config/hearsay.go`. This avoids an unrelated peer network exposing the host address despite remote-only torrent acquisition. Verify the saved settings and absence of participation messages; an isolated fixture container exposed the default without sending traffic to external peers.

Run Python contract tests for a fresh configuration, repeat activation with byte-identical state, secret rotation without token regeneration, existing signing-key preservation, malformed-state refusal, restrictive permissions and interruption-safe writes. ## Risks / Trade-offs

- [HolyArrs with Decypharr is untested end to end; categories and magnet redirects may break grabs] → Test a cached movie and provision required categories declaratively; a different downloader requires a revised design, not a manual workaround.
- [HolyArrs may hash a whole file through the link on rename or delete (issue #158)] → Accept for the test; watch Real-Debrid traffic during renames.
- [Music availability varies by source and Real-Debrid support] → Verify the selected debrid path with a real album; metadata discovery does not guarantee acquisition. Source changes must be repository-managed; no local torrent fallback is permitted.
- [Public trackers behind Cloudflare need FlareSolverr] → Use indexers that work without it for the test; add FlareSolverr later if needed.
- [HolyArrs versions and APIs evolve] → Pin versions, change pins in Git, and retest bootstrap, integrations and recovery before rollout.
- [`SYS_ADMIN` + `/dev/fuse` widen the Decypharr container's privileges] → Only on kaito, only reachable over the mesh, image pinned.
- [`HOLYARRS_ALLOWED_HOSTS` value format is not documented in detail] → If the hostname is rejected, use `http://10.123.0.1:6262`, which works without it.
- [Fixed uid/gid 2000 could collide on kaito] → Check `getent passwd 2000` / `getent group 2000` on kaito before deploying.

## Migration Plan

1. Resolve the implementation gates and update the concrete design and application-specific tasks before implementation. Preserve historical baseline results separately from the new acceptance criteria.
2. Build affected NixOS and Home Manager configurations. Test unattended fresh installation and repeated activation in a disposable VM before touching kaito.
3. With explicit deployment approval, copy and activate the configuration on kaito; provisioning runs automatically after required secrets and services are ready. Running a deployment command is not web configuration.
4. Test a movie through playback and an unowned album through discovery, HolyArrs acquisition, availability refresh and automatic playback. Verify restart, mount-loss, rebuild and recovery behaviour.
5. Keep Navidrome, AIOStreams and original libraries available throughout migration. Decommission only after equivalent replacement workflows pass and removal is approved.
6. **Rollback:** activate the previous generation or remove newly introduced imports and rebuild, retaining state, keys and original media data. Do not delete state during rollback.
